Throughput And Latency

Throughput and latency measure related but different things. Throughput is completed requests per measured second, while latency percentiles describe only selected points in the request distribution. With a fixed closed-loop concurrency, a server can show better p50 or p95 latency and still have lower throughput if more time is spent in tail requests, scheduling, GC, process coordination, or other overhead that reduces total completions.

Use the raw rows when this happens: compare completed requests, measured duration, p50, p95, p99, p99.9, CPU, RSS, and errors together. A lower p50 with a worse p99 or fewer completions usually means the common case got faster but some request slots stayed occupied long enough to pull throughput down.

Caveats

  • This is a local closed-loop benchmark using Ruby's Net::HTTP, not a replacement for wrk or wrk2.
  • Warmup requests are discarded from latency and throughput numbers.
  • RSS and CPU charts depend on ps. If process sampling is unavailable, memory cells may be blank.
  • Puma cluster GC deltas are intentionally blank in summary columns because a normal HTTP metrics probe samples one worker, not the full cluster.
  • Adapter comparison tables and charts aggregate repeats by server/runtime/scenario/capacity first, then present Puma and Raptor rows within the same request-slot capacity groups.
  • Use raw absolute numbers first. Percentage deltas only make sense beside latency, throughput, RSS, CPU, errors, and workload context.
